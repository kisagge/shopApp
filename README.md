# PLAIN — 커머스 웹/앱 (포트폴리오)

Next.js 모노레포로 만든 쇼핑몰. **하나의 코드베이스**가 반응형 웹으로 돌고,
같은 것을 Capacitor 셸로 감싸 iOS/Android 앱이 된다. 안드로이드는 실기기에,
iOS 는 시뮬레이터에 설치해 확인한 상태다.

한국어·영어·일본어로 나가고, 손님 화면부터 가맹점·운영진 화면과 정산·배치까지
한 저장소 안에 있다.

브랜드명 **PLAIN**과 사업자 정보는 플레이스홀더다. 사업자등록번호가 선수로
필요한 기능(실결제 정산, 본인인증 등)은 처음부터 범위에서 뺐다.

## 이렇게 정한 것들

### 모바일을 원격 셸로

Capacitor 는 Next.js 의 서버 기능(RSC, Route Handler)을 기기 안에서 실행할 수
없다. 그래서 두 갈래가 있다 — ① 전부 정적 export 해서 번들하거나(RSC/SSR 포기),
② 배포된 웹을 네이티브 셸이 로드하고 네이티브 기능만 브릿지로 쓰거나.

**②를 택했다.** 코드가 100% 공유되고, 공유·딥링크·스플래시 같은 것은
`packages/native` 파사드가 웹에서는 Web API 폴백으로, 앱에서는 Capacitor
플러그인으로 갈라져 동작한다. 화면 코드는 자기가 어디서 도는지 모른 채 쓴다.

그 파사드는 **npm 의존성이 0 이다.** `@capacitor/*` 를 웹 번들에 넣으면
브라우저에서 쓰지도 않을 코드를 받게 되므로, `window.Capacitor.Plugins.*` 를
직접 본다.

### 정책은 core 에, 계약은 contract 에, 실행은 앱에

무엇이 규칙인지(`packages/core`)와 무엇이 오가는지(`packages/contract`)를
실행에서 떼어 놓았다. 배송비·할인·주문 상태 전이·권한·매출 인식은 I/O 가 없는
순수 함수라 빠르게 검사할 수 있고, 화면과 API 가 같은 답을 본다.

### 규칙을 기억이 아니라 검사로 지킨다

이 저장소에서 가장 많이 쓴 방법이다. **목록을 손으로 들고 있으면 반드시 샌다.**
그래서 목록을 파일 시스템이나 코드에서 만들고, 빼려면 이유를 적게 한다.
그리고 **고친 것을 되돌려서 검사가 실제로 지는지 확인한 뒤에** 커밋한다.

실제로 잡힌 것들:

| 검사 | 잡은 것 |
|---|---|
| `rate-limit-coverage` | 요청 제한 목록 밖에 라우트 18개가 있었고 **그중 주문 생성**이 있었다 |
| `a11y-coverage` | 손으로 적은 훑기 목록이 화면 10장을 놓쳤고 **그중 결제 화면**이 있었다 |
| `validation-message-coverage` | 스키마 40개가 제약을 어기면 Zod 의 **영어 기본 문구**로 답하고 있었다 |
| `client-dictionary` | 한국어 화면 하나가 **영어·일본어 사전까지** 내려받고 있었다(gzip 24KB) |
| `cron-coverage` | 배치가 vercel.json 에 등록됐는지 — 등록을 빼먹으면 조용히 안 돈다 |
| `dead-exports` | 부르는 곳이 없는 export |
| `e2e-coverage` | Playwright 프로젝트에 안 잡혀 **한 번도 안 도는** 스펙 파일 |
| `layout` | 좁은 화면에서 글자가 상자를 넘치거나 본문이 가로로 스크롤되는 것 |
| `layout` (글자기둥) | 넘치지는 않는데 **한 자씩 세로로 서는** 글자 — 상품 비교의 줄 제목이 세 줄이었다 |
| `dark-contrast` | 화면에 **실제로 칠해진 색**으로 잰 명암비 — 토큰을 안 쓴 자리가 여기서 걸린다 |
| `theme-flip` | 밝은 화면에서 잔잔하던 선이 어두운 화면에서 **흰 선**이 되는 것 |
| `audit-coverage` | 운영진의 쓰기가 감사 로그에 닿는지 |
| `cart-isolation` | 장바구니를 쥐는 명세가 계정을 나눠 쓰는 것 — 산발로 지는 원인이었다 |
| 시드 자기검사 | 파생 칸(검색·판매가)이 원본과 어긋난 상품, **적립 원장이 빠진 구매확정 주문** |

### 숫자는 재고 나서 말한다

성능·용량은 추측하지 않고 실제로 잰다. 예를 들어 사전을 코드가 아니라 데이터로
내려보내는 변경은 홈 화면 전송량을 **gzip 294.6KB → 271.4KB** 로 줄였다
(스크립트 −36.7KB, HTML +13.5KB — 첫 방문이 이기고 하드 리로드가 지는 트레이드를
알고 택했다).

### 앱으로 돌려 보기

```bash
pnpm mobile:sync                       # 웹 셸 자산 동기화
CAP_SERVER_URL=http://<내 IP>:3000 pnpm mobile:android
```

안드로이드 빌드에는 **Android Studio 가 들고 있는 JDK** 가 필요하다. Capacitor 8 은
Java 21 을 겨냥하는데 보통 설치돼 있는 JDK 는 17 까지다 —
`/Applications/Android Studio.app/Contents/jbr/Contents/Home` 을 `JAVA_HOME` 으로 준다.

iOS 는 Xcode 로 열지 않고도 시뮬레이터까지 갈 수 있다.

```bash
pnpm mobile:sync
cd apps/mobile/ios/App && xcodebuild -scheme App -sdk iphonesimulator \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' \
  -derivedDataPath /tmp/plain-ios build
xcrun simctl boot 'iPhone 17 Pro'
xcrun simctl install booted /tmp/plain-ios/Build/Products/Debug-iphonesimulator/App.app
xcrun simctl launch booted test.plain.shop
```

**뒤로 가기는 플랫폼마다 다른 자리에서 다룬다.** 안드로이드의 뒤로 가기 버튼은
웹 쪽 `native-back-button.tsx` 가, iOS 의 가장자리 밀기는 `AppDelegate` 가 맡는다.
밀기는 WKWebView 설정이라 웹에서 손댈 수 없고 Capacitor 가 설정 파일로 열어 두지도
않아서, 웹뷰가 화면에 올라온 뒤 켠다. 처음에는 이것이 빠져 있어 **iOS 에서 밀어도
아무 일도 안 했다.**

딥링크를 실제로 검증하려면 `ANDROID_CERT_SHA256` 과 `APPLE_TEAM_ID` 를 채우고
Xcode 에서 Associated Domains 를 켜야 한다. 자세한 것은 `apps/mobile/README.md`.

## 접근성

모든 컴포넌트는 시맨틱 HTML 로 짠다. `div` 남발 대신 `header`/`nav`/`main`/`section`/
`article`/`dl`/`table` 을 쓰고, 아이콘 전용 버튼에는 `aria-label`, 폼 에러는
`aria-invalid` + `aria-describedby` + `role="alert"` 로 연결한다.
**상태를 색·모양으로만 전달하지 않고** 항상 글자를 함께 둔다 — 상품 비교표에서
가장 나은 값을 굵게 칠할 때 낭독기용 문구를 함께 넣는 식이다.
포커스 링은 제거하지 않고 `:focus-visible` 로 노출한다.

손님·회원·운영진 화면을 axe 로 훑고(`e2e/a11y-*.spec.ts`), 훑기가 화면을 빠뜨리지
않는지는 `a11y-coverage` 가 파일 시스템과 대조해 지킨다.

**어두운 화면도 함께 잰다.** 토큰 대비 검사는 설계한 값끼리 재는데, 화면에 나오는
색은 토큰만이 아니다 — 저울의 눈금(`text-n-500` 같은 것)을 직접 부른 자리는 테마가
바뀌어도 안 바뀐다. 그래서 `dark-contrast` 는 **브라우저가 실제로 칠한 색**을 읽어
밝은 화면과 어두운 화면 양쪽에서 재고, `theme-flip` 은 같은 선이 한쪽에서는
잔잔하고 다른 쪽에서는 또렷해지는 것을 잡는다. 정가 취소선(3.81:1), 정산의 환불
금액(3.66:1), 입력 칸 테두리(밝은 1.6:1 → 어두운 12:1)가 여기서 나왔다.

**어두운 화면을 사람이 고를 수 있다.** 한동안 기기 설정(`prefers-color-scheme`)만
따라갔다 — CSS 에는 `:root[data-theme="dark"]` 규칙이 이미 있었는데 그 값을 세우는
코드가 없어 쓰이지 않는 규칙 한 벌이 누워 있었다. 이제 매장 푸터와 운영 사이드바
양쪽에서 시스템·밝게·어둡게를 고르고, **언어와 같은 폼 전송**이라 스크립트 없이도
바뀐다. 운영 사이드바는 테마와 무관하게 늘 어둡게 설계돼 있어서, 거기 단추 위에는
바뀌는 것이 본문이라고 적어 둔다 — 안 적으면 눌러도 안 먹는 것으로 읽힌다. 서버가 쿠키를 읽어
`<html data-theme>` 를 박으므로 첫 그림부터 그 밝기다 — 브라우저에서 칠하면 어두운
방에서 흰 화면이 한 번씩 번쩍인다. 상태바(`theme-color`)와 브라우저가 그리는
것(`color-scheme`: 스크롤바·기본 폼 위젯)도 함께 따라간다.

**시드도 앱의 규칙을 지킨다.** 앱에서 구매확정은 언제나 적립과 함께 일어나는데
(상태를 바꾸는 그 트랜잭션 안에서 원장을 쓴다), 시드는 확정된 주문을 곧바로
만들어 와서 **확정 주문 293건에 구매 적립 원장이 한 줄도 없었다.** 포인트 화면에는
가입 축하 포인트만 보였고, 소멸 예정과 정산 배치는 볼 것이 없었다. 규칙이 앱 경로에만
있으면 시드가 만든 데이터는 그 규칙 밖에 산다 — 검색 칸이 비어 검색이 0건이던 것과
같은 자리다. 이제 시드가 채우고, 채운 뒤 **스스로 확인한다**(확정 주문마다 원장
정확히 하나 · 잔액 = 원장 합).

**재고 부족은 넘는 순간 한 번만 알린다.** 대시보드에도 "재고 부족" 이 뜨지만 열어야
안다. 주문이 옵션 재고를 기준(5개) 아래로 **넘기는 순간** 그 가맹점 계정들의 운영
알림함에 한 줄 남긴다 — "기준 이하면 알림" 으로 하면 품절까지 주문마다 쌓여 다섯
통째에는 아무도 안 읽는다. 넘겼는지는 **트랜잭션 안에서** 본다: 방금 깎은 줄은 이
트랜잭션이 잠그고 있어서 이 주문이 깎은 직후의 값이 나오고, 커밋 뒤에 읽으면 그 사이
다른 주문이 깎은 것까지 섞인다. 기준 5 는 상품 화면·대시보드·운영 상품 목록에 **따로
박혀 있었는데** 알림까지 넷째로 박기 전에 core 한 곳으로 모았다.

알림함을 매장과 운영으로 가르면서 **읽음 처리 창구가 새고 있었다** — 종류를 가리지
않아서 매장 알림함을 한 번 여는 것만으로 운영 알림까지 읽음이 됐다. 가맹점이 매장에
들렀다 가면 재고 뱃지가 조용히 사라지는 셈이다.

**카테고리도 바꿀 창구가 없었다.** 매대의 카테고리 조회에 "창구가 없어서 거의 바뀌지
않는다" 고 적혀 있다 — 캐시를 길게 잡아도 되는 이유로 적은 말이지만, 관리 화면이 없다는
사실을 돌려 말한 것이기도 하다. 시즌마다 갈래를 더하려면 DB 콘솔을 열어야 했고, 머리 메뉴의
순서(`sortOrder`)도 시드만 썼다.

나무를 그리고 **위·아래 단추로 순서를 옮긴다** — 끌어다 놓기는 키보드와 낭독기에게 거의 닫힌
길이고, 갈래가 열 몇 개뿐이라 단추로 충분하다. 규칙 셋을 화면과 서버가 함께 막는다:
**두 단까지**(머리 메뉴가 그 아래를 안 그려서, 손자를 만들면 어디에도 안 보이는 갈래가 된다),
**상품이 붙은 갈래 밑에는 못 만든다**(상품은 말단에만 붙는데 밑에 자식이 생기면 그 상품들이
어느 쪽으로 세어도 빠진다 — 시드의 슈즈·액세서리가 정확히 그 모양이다: 최상위인데 상품을
가진다), **비어 있을 때만 지운다**. 주소를 바꾸면 브랜드와 같이 옛 주소가 새 주소로 넘어간다.

가맹점에게는 열지 않는다 — 브랜드는 그 가맹점의 간판이라 자기 것을 고칠 수 있지만,
카테고리는 매대 전체의 갈래라 누구의 것도 아니다.

**상품 폼의 카테고리 목록이 `sortOrder` 를 무시하고 주소순으로 서 있었다.** 매대에서는
코트·패딩·자켓인데 폼에서는 영문 순이었다 — 순서를 고칠 수 있게 되었으니 더 어긋난다.

**시드 말고는 브랜드를 쓰는 곳이 없었다.** 화면도 API 도 없어서, 입점 승인 때 자동으로
만들어진 브랜드는 만들어진 그대로 굳었다 — 한글 이름이면 라틴 문자가 남지 않아 주소가
`brand-a1b2c3d4` 가 되는데, **그 자리의 주석은 "나중에 가맹점이 직접 고칠 수 있다" 고 적어
두었지만 고칠 자리가 없었다.** 그 약속을 지키는 화면을 둔다. 가맹점도 들어오되 자기
브랜드만 본다: 이름과 주소는 매대에 그대로 뜨는 값이라, 남의 것을 고칠 수 있으면 그 가게의
간판을 바꿔 다는 셈이다. 만들기는 운영진만 — 가맹점의 간판은 입점 승인이 만드는 하나이고,
스스로 더 만들면 정산·범위 판단이 함께 흔들린다.

**주소를 바꾸면 옛 주소를 남긴다**(`BrandSlug`). 안 남기면 그때까지 나간 링크가 죽고 화면에는
멀쩡한 404 가 나와 아무도 사고인 줄 모른다 — 상품·기획전에서 같은 이유로 이미 두 번 겪었다.
넘길지 말지는 core 의 `slugLookup` 이 정한다. **그 함수는 쓰이는 데 없이 놓여 있었다**: 되돌린
경우(a → b → a)에 기록을 먼저 보면 자기 자신으로 넘기는 고리가 생긴다는 판단을 담아 두고도,
세 화면이 각자 순서를 적고 있었다. 여기서 처음 불린다.

**주문 접수·가상계좌 발급·입금 확인만 메일로만 나갔다.** 배송·취소·환불·반품은 전부
알림함에도 남는데, **가장 많이 오가고 가장 마음 졸이며 확인하는 세 가지**가 빠져 있었다 —
알림함을 만든 이유가 "메일은 놓치기 쉽고 스팸함으로 가기도 한다"(`deliver.ts`) 인데, 정작
돈이 오가는 자리에는 그 대비가 없었다. 셋 다 `deliverNotice` 로 옮겨 메일과 알림함에 함께
간다(그래서 함수 이름도 `sendOrderMail` → `deliverOrderNotice` 로 바꿨다 — 메일만 보내지
않는다). 가상계좌 알림은 **계좌가 적힌 주문 화면으로** 데려간다: 위의 두 고침이 여기서 만난다.

**계좌를 받아 두고 보여 주지 않았다.** 가상계좌 셋(은행·번호·기한)을 결제 때 저장하는데
**읽는 곳이 어디에도 없었다** — 주문 조회는 `payment: { method, status }` 만 가져왔고, 화면은
"결제가 확인되면 배송 준비를 시작합니다" 만 말했다. 번호를 볼 수 있는 자리는 결제 직후 한 번
뜨는 응답과 메일뿐이라, **탭을 닫았거나 메일이 스팸함에 갔으면 그 주문은 화면에서 입금할
방법이 없었다.** 돈이 걸린 자리다.

재결제 안내와는 겹치지 않는다. `isRepayable` 이 입금 대기를 빼는 것은 맞다 — 그때 할 일은
송금이지 재결제이고, 다시 걸면 이미 받은 계좌를 버려 옛 계좌로 넣은 돈이 갈 곳을 잃는다.
다만 그 "재결제가 아니다" 가 **"아무 말도 안 한다"** 가 되어 있었다. 기한이 지난 것도
보여 준다: 만료됐다는 사실 자체가 알아야 할 소식이고, 그때 할 일(취소하고 다시 주문)을
화면이 안내할 수 있다.

**반려 사유를 정작 운영진이 못 봤다.** 신청한 사람은 신청 화면에서 보는데, 반려한
쪽에는 볼 자리가 없어 감사 로그를 뒤져야 했다. 가맹점 상세 화면을 두고 거기 놓는다 —
목록 한 줄에 다 담을 수 없는 것들(신청서에 적어 낸 것, 붙어 있는 브랜드·계정·상품·정산,
지난 기록)이 함께 산다. **못 하는 일을 미리 말한다**: 반품지가 없으면 반품을 승인할 수
없고 계좌가 없으면 정산을 지급할 수 없는데, 그때 가서 막히는 것보다 여기서 보이는 편이 낫다.

지난 기록을 놓으려니 감사 로그에 **대상 하나로 좁히는 길이 없었다** — 종류(`merchant`)로만
걸러서 모든 가맹점의 기록이 섞여 나왔다. `targetId` 를 더했다. 가맹점 계정에게는 이 칸을
아예 묻지 않는다: 누가 언제 정지했는지까지 보여 줄 이유가 없다.

**서른한 번째 알림은 볼 길이 없었다.** 알림함은 서른 개를 잘라 오고 그게 끝이라, 그
아래는 주소로도 못 갔다 — 알림은 지워지지도 않으니 조용히 쌓이기만 했다(정렬에 `id` 가
딸려 있던 것은 언젠가 넘길 생각이었다는 흔적이다). 매장·운영 알림함 둘 다 운영 목록과
같은 쪽 번호를 쓴다. **범위를 넘은 쪽은 마지막 쪽을 보여 준다** — 즐겨찾기에 담아 둔 쪽은
알림이 지워지면서 사라지고, 그때 빈 화면을 주면 "왜 아무것도 없지" 로 끝난다. 넘쳤을 때만
한 번 더 읽는다(세고 나서 읽으면 멀쩡한 쪽까지 왕복이 하나 는다).

**여덟 군데가 한꺼번에 같은 구멍을 갖고 있었다.** 쪽 번호를 붙이면서 받은 숫자를 그대로
`offsetOf` 에 넣었고, 화면의 쪽 번호만 core 의 `pageNav` 로 당겨 그렸다 — `?page=999` 는
마지막 쪽이 칠해진 채 목록만 빈 화면이 됐다. 한 군데를 고치고 나머지를 잊기 쉬운 모양이라
도우미(`queries/paged.ts`) 하나로 모으고, `offsetOf` 를 쓰는 조회는 그것을 써야 한다는
검사를 뒀다(고친 것을 되돌려 검사가 지는 것까지 보고 넣었다).

**보존 정책은 적혀 있었는데 아무도 지우지 않았다.** core 에 90일과 자르는 시각이 있고
주석에는 "배치가 지운다" 고 되어 있었지만 **부르는 곳이 한 군데도 없었다.** 하루치 정리
배치(이벤트 롤업과 같은 자리)에서 함께 지운다 — 크론을 하나 더 두지 않는 이유는 배포
플랜마다 개수 제한이 있어서다. **읽은 것만 지운다**: 안 읽은 것은 오래됐어도 그 사람이
아직 못 본 소식이고, 그 판단을 대신 내리면 "왜 알림이 사라졌냐" 에 답할 수가 없다.

**사유는 받고 있었는데 닿지 않았다.** 검수 반려는 사유 없이는 못 하게 막혀 있고
(`REJECT_REASON_REQUIRED`) 그 이유도 적혀 있었다 — "이유 없이 되돌리면 가맹점은 무엇을
고쳐야 할지 알 수 없고, 그대로 다시 올려서 같은 일이 반복된다". 그런데 그 글을 상품 행에
**적어 두기만** 했다. 가맹점은 자기 상품을 다시 열어 봐야 그것을 보는데, 검수는 며칠
걸리는 일이라 다시 열어 볼 이유가 없다. 승인·반려 둘 다 운영 알림함으로 보낸다(승인도
알린다 — 안 알리면 며칠째 대기줄인 줄 안다). 사유는 500자까지 받으므로 알림 한 줄에는
**80자로 줄이고 …을 붙인다**: 그냥 자르면 문장이 끝난 줄 알고 뒤에 붙은 조건을 못 본다.
전문은 눌러서 가는 상품 화면에 있다.

**반려라는 상태가 없어서 해지를 대신 쓰고 있었다.** 가맹점 상태는 `PENDING · APPROVED ·
SUSPENDED · TERMINATED` 넷이라, 심사에서 되돌린 신청도 "해지" 로 적혔다 — 나중에 읽는
사람은 이 가맹점이 장사를 하다 그만둔 것인지 애초에 들어온 적이 없는 것인지 가릴 수
없었다. 신청 화면의 안내 키가 `merch.rejected` 인데 **해지에 붙어 있던 것**이 그 증거다.

`REJECTED` 를 더하고 **갈 수 있는 곳을 core 가 정한다.** 심사 중인 신청은 승인하거나
반려하고(정지·해지는 장사하던 가맹점에 내리는 처분이다), 끝난 줄은 되살리지 않는다 —
다시 들어오려면 새로 신청하고, 그러면 새 줄이 생겨 지난 판단이 남는다. 운영 화면은 갈 수
없는 곳을 **아예 안 보여 준다**: 고를 수 있게 두고 서버가 튕기면 누른 사람은 자기가 무엇을
잘못했는지 모른다. "사유가 필요한 처분" 도 계약과 화면이 각자 적고 있던 것을 core 한 곳으로
모았다(상태가 하나 늘 때 한쪽만 고치면 화면은 사유를 안 받고 서버가 튕긴다).

그리고 **결과를 신청한 사람에게 알린다.** 승인은 계정과 브랜드까지 만들어 주면서 아무 말도
안 해서 신청자는 로그인해 보고서야 알았고, 반려 사유는 감사 로그에만 남았다. 둘 다 매장
알림함으로 간다 — 반려된 사람에게는 운영 화면이 아예 없다. 사유는 알림에 80자로 줄여 싣고
전문은 신청 화면에 둔다(`Merchant.rejectionReason`, 상품 검수의 `publishRejection` 과 같은 결).

**쿠폰 알림만 갈 곳 없이 쌓이고 있었다.** 칸 이름은 `linkPath` 인데 `href` 라고 적혀
있었고 타입 검사도 린트도 통과했다 — 초과 속성 검사는 **갓 만든 객체 리터럴**에만 걸리는데,
`list.map((x) => ({ … }))` 는 map 이 타입을 스스로 지어내므로 그 배열을 넘기는 것은 그냥
부분형 검사가 된다. 개발 DB 에서 다른 종류는 전부 링크가 있는데 그것만 0건이었다. map 에
돌려주는 타입을 적게 하고(그러면 다시 걸린다), 알림을 적는 파일에 `href` 를 쓰지 못하게
검사를 뒀다.

**일부 상품 취소는 돈이 새는 자리를 셋 막는다.** 줄 하나를 무르면 ① 그 줄에 붙은 쿠폰 할인은
돌려주지 않는다(안 그러면 쿠폰을 쓰고 비싼 줄을 취소하는 것만으로 할인이 현금이 된다) ② 남은
상품이 무료배송 기준 아래로 떨어지면 원래 냈어야 할 배송비를 뗀다 ③ 나중에 나머지를 전부 취소하면
**받은 것 − 이미 돌려준 것**만 돌려주고, 뗀 배송비도 돌려준다. 어느 줄이 쿠폰 대상이었는지는
취소하는 날에는 알 수 없어서(분류가 바뀐다) **주문할 때 줄마다 몫을 나눠 박고**, 배송비 기준도
주문한 날의 것을 스냅샷으로 남긴다. 나눌 때는 최대 나머지법으로 원 단위를 흘리지 않는다.
두 사람이 같은 주문의 다른 줄을 동시에 취소하면 둘 다 "아직 배송비를 안 뗐다" 를 보고 계산하므로,
주문 행을 잠그고 그 안에서 다시 읽는다. 매출과 정산은 이제 주문 상태가 아니라 **환불 기록과 줄의
취소 시각**으로 환불을 센다 — 일부 취소한 주문은 결제완료인 채로 남기 때문이다. 옛 환불은 마이그레이션이
같은 조건으로 옮겨 적었다. e2e 는 일부 취소 뒤 전액 취소의 환불 합이 결제 금액과 같은지 본다 —
전액 취소를 옛 방식으로 되돌리면 238,000원이 357,000원이 되어 진다.

**반품도 줄 단위다.** 코트와 니트를 받아 니트만 작으면 니트만 돌려보낸다. 손님이 고른 줄만
반품접수가 되고, 운영자는 승인한 뒤 물건이 돌아오면 "회수 확인 · 환불" 한 번으로 그 줄 몫만
돌려준다 — 누르기 전에 금액이 보인다. 일부 취소와 같은 계산을 쓰되 셋이 다르다: 배송비는 **단순
변심일 때만** 떼고(판매자 잘못으로 돌려보낸 물건 때문에 배송비를 물 이유가 없다), 재고가 돌아오고,
구매확정 뒤라면 **그 줄의 적립 몫만** 되가져온다(적립 회수는 원장이 하나라도 있으면 건너뛰던
것을 "가져간 만큼 빼고" 로 고쳤다 — 안 그러면 나머지를 반품할 때 남은 적립을 영영 안 가져온다).
주문은 남은 줄을 따라 배송완료·구매확정으로 돌아간다. 정산은 줄에 **"확정 뒤에 돈이 돌아갔다"**
를 적어 두고 그것으로 가른다 — 주문 상태로 가르면 한 줄만 반품한 구매확정 주문이 지난달 판매에서
소리 없이 빠지거나, 이미 지급한 달이면 차감이 영영 안 된다.

**반품의 판단은 물건 곁에서, 돈은 운영진이.** 반품된 물건을 받는 곳은 가맹점 창고다. 운영진이 승인하고
도착까지 확인하게 두면 물건을 본 적도 없이 "도착했다" 를 누르게 된다. 그래서 `return:resolve`
(승인·반려·도착 확인)를 가맹점에게도 주고, 돈을 내보내는 `order:refund` 는 운영진에게 남긴다 —
가맹점이 자기 상품 반품에 스스로 돈을 돌려줄 수 있으면 권한을 나눈 뜻이 없다. 한 주문에 두 가맹점
상품이 섞였고 신청이 둘 다 돌려보내는 것이면 운영진이 처리한다(한 가맹점이 남의 반품까지 승인하게
된다). 운영 화면은 가맹점이 확인한 시각을 보고 "환불" 만 누른다. e2e 는 가맹점·운영진·손님이 각자
자기 화면에서 한 바퀴를 밟고, 가맹점 화면에 환불 단추가 새면 진다.

**재고도 파일로 고친다.** 창고 실사는 엑셀에 맞춰 적는 것이 보통이라, 재고 파일을 내려받아 숫자만
고쳐 올린다. SKU 로 옵션을 가리고(상품 이름은 겹치고 바뀐다), 적용은 상품 화면의 재고 수정과 **같은 함수**를
상품마다 부른다 — 범위·재입고 알림·감사 로그가 갈리지 않게. 소수·글자·같은 SKU 의 다른 숫자는 추측하지
않고 줄 번호로 돌려주고(1.5 를 1 로 읽으면 실사 수량이 조용히 틀린다), 값이 그대로인 줄은 건드리지 않는다.
남의 SKU 는 없는 SKU 와 똑같이 답해 넣어 보는 것으로 다른 가맹점 상품을 알아낼 수 없다. 받은 뒤 오래
들고 있으면 그 사이 팔린 만큼이 되살아나므로 화면이 실사 직전에 받으라고 말한다 — e2e 도 그래서 파일
전체가 아니라 자기 상품의 줄만 올린다.

**정산 내역은 화면의 정산과 같은 줄이다.** 합계 한 줄로는 가맹점이 자기 장부와 맞춰 볼 수 없어서, 판매 줄과
차감 줄을 하나씩 내려주고 끝에 가맹점마다 판매·수수료·차감·지급액을 붙인다. 줄을 고르는 조건은 정산 초안과
**한 함수**다 — 따로 적으면 파일의 합이 화면과 어긋나고 어느 쪽도 믿을 수 없다. e2e 가 받은 파일의 판매 줄 수·
판매 합·지급액을 초안의 줄과 맞춘다. 그 조건을 모으다 **판매를 "지금 구매확정 상태인 주문"으로 고르고 있던**
것을 찾았다 — 확정 뒤 주문째 반품되면 그 달 판매에서 빠지고 차감에는 잡혀 같은 달이면 가맹점이 두 번 깎인다.
판매는 확정된 적이 있는지(확정 시각)로 고른다.

**품절 옵션을 키보드로 밟아 봤다.** 재입고 알림을 열려고 품절 옵션을 고를 수 있게 바꾸자 화살표도 품절 옵션에 멈춘다
(라디오는 옮기는 순간 골라진다). 그 길을 키보드로 끝까지 밟으니 둘이 걸렸다. 하나, 수량을 4 로 올려 두고 재고 1 개인
사이즈로 **지나가기만 해도** 4 가 그대로 담겼다 — 이제 그릴 때 고른 옵션의 재고로 자르고(올려 둔 값은 남겨 두어 재고
많은 옵션으로 돌아가면 살아난다), 담을 때도 그 값을 쓴다. 둘, 색을 화살표로 옮겨 골라 둔 사이즈가 품절이 되면 담기
단추가 재입고 알림으로 바뀌는데 초점은 색에 있어 **낭독기가 아무 말도 안 했다** — 늘 그려 둔 알림 영역이 "품절입니다,
재입고 알림을 신청할 수 있습니다" 를 말한다. 탭 한 번에 묶음 하나·Home/End·끝에서 처음으로 도는 동작과 함께 단위
검사로 잡고, 재입고 e2e 는 실제 브라우저에서 키보드만으로 품절 옵션에 닿아 Enter 로 신청한다.
같은 판에서 리뷰 등록 알림이 곧바로 사라지던 것도 잡혔다 — 등록하면 그 상품이 목록에서 빠지며 폼과 함께 "리뷰를
등록했습니다" 가 없어졌다(마지막 한 개면 "쓸 수 있는 상품이 없습니다" 만 남았다). 이제 결과를 주소에 싣고 화면이 남긴다.

**후기에 적립금을 준다 — 사진이 있으면 더.** 색이 화면과 얼마나 다른지, 소재가 어떻게 떨어지는지는 글로 적기 어렵고 대개
안 적는다. 그래서 값을 다르게 뒀다(글 100P, 사진 500P). 금액은 정액이다 — 산 금액에 비례하면 비싼 물건의 후기만 값어치가
있는 셈이 되는데, 후기의 쓸모는 가격이 아니라 내용에서 나온다. **셈의 기준은 리뷰가 아니라 주문 항목이다**: 본인이 지운
리뷰는 행이 남지 않아 같은 구매로 다시 쓸 수 있어서, 리뷰로 세면 썼다 지웠다를 되풀이해 적립금을 찍어낼 수 있다 —
원장이 그 기억을 맡는다(`PointTransaction.orderItemId`). 리뷰를 고쳐 사진을 붙이면 차액을 주고, 사진을 빼거나 글을
지웠다고 빼앗지는 않는다(이미 받은 것을 도로 가져가려면 쓴 사람에게서 빼앗아야 한다). 적립은 글이 올라가는 **그
트랜잭션 안에서** 나간다 — 밖에서 주면 글은 올라갔는데 적립이 실패하는 구간이 생기고, 그건 아무도 모른다.

**운영 목록을 쪽 번호로 넘긴다 — « ‹ 1 2 3 4 5 › »** 예전에는 커서식 "더 보기" 였고, 그 선택에는 이유가 있었다:
보는 사이 앞에 행이 끼어들어도 같은 행을 두 번 보여 주지 않는다. 그런데 운영 목록은 **훑고 처리하는 자리**다 —
일곱 쪽 뒤의 주문을 보려고 여섯 번을 눌러야 했고, 지금 어디쯤인지도 알 수 없었다. 그 불편이 겹쳐 보이는 한 줄보다
크다고 보고 바꿨다(내준 것은 주석에 적어 두었다). 주문·상품·회원·반품·리뷰·문의·감사 로그 일곱 화면이다.

**끝에 닿은 화살표는 링크가 아니다.** 눌러도 같은 자리로 오는 링크를 두면 낭독기는 갈 곳이 있는 것처럼 읽고,
키보드 사용자는 탭 순서에 쓸모없는 정거장을 하나 더 만난다. 지금 쪽도 링크가 아니라 `aria-current="page"` 로
말한다 — 굵게만 그리면 눈으로만 보이는 상태다. 번호 묶음은 지금 쪽을 가운데 두되 **끝에서는 밀어 붙인다**:
1쪽에서 가운데를 고집하면 폭이 줄어 누르려던 자리가 쪽을 넘길 때마다 움직인다.

**찜·도움돼요 하트를 그림으로 바꿨다.** `♥`(U+2665)와 `♡`(U+2661)는 서로 다른 **문자**라 기기마다 다른 폰트에서
온다 — 안드로이드는 찬 하트를 컬러 이모지로, 빈 하트를 텍스트 폰트로 그려서 앱에서 켠 것과 끈 것의 크기·굵기가
달라 보였다(PC 는 둘 다 같은 폰트라 티가 안 났다). 같은 path 하나를 두고 채우기만 바꾼다.

**브라우저에서 난 오류를 받고, 오류를 지문별로 모아 본다.** 서버 오류는 `instrumentation` 이 받아 로그와 메일로
나가고 있었는데 **브라우저에서 터진 것은 아무도 몰랐다** — 그 기기에서만 일어난 일이고, 앱(웹뷰)에서는 개발자 도구도
배포 로그도 없다. 화면이 하얗게 뜬 채로 사용자는 "안 돼요" 라고만 말할 수 있다. 이제 화면 경계(`error.tsx`)와
`window` 의 오류·거절을 받아 같은 길로 보낸다(지문·심각도·가림 규칙을 나누면 같은 오류가 두 벌로 쌓인다). 같은 오류는
한 화면에서 한 번만 보낸다 — 렌더 하나가 깨지면 리렌더마다 또 나기 때문이다.

그리고 **오류가 어디에도 남지 않았다.** 콘솔과 메일뿐이었고 메일은 같은 지문을 한 시간에 한 번만 보내니, "이 오류가
몇 번 났는가" 에 답할 곳이 없었다. 지문 하나에 행 하나를 두고 횟수와 처음·마지막 시각을 센다(한 건마다 남기면 표가
금방 커지고 매번 세어야 한다). 운영 화면에서 처리 표시를 달 수 있고, **처리한 뒤에 또 나면 스스로 다시 열린다** —
조용히 횟수만 올리면 닫힌 목록 뒤에 숨어 처리 표시가 오히려 눈을 가린다. 사용자 id 는 남기지 않는다: 고칠 때 필요한
것은 어느 화면에서 무엇이 터졌는가이지 누구인지가 아니다.

**웹 표준·접근성을 훑어 열한 군데를 고쳤다.** axe 훑기가 모든 화면을 통과하고 있었는데도 남아 있던 것들이다 — 도구가
못 보는 자리가 있다. `<label>` 이 체크박스와 링크를 함께 감싸 동의 항목 이름이 "…동의합니다 읽기" 로 읽히던 것(axe 의
nested-interactive 는 위젯 role 이 붙은 컨테이너만 본다), `aria-describedby` 가 **그리지 않는** 힌트를 가리키던 것,
신고·비밀번호 찾기에서 폼이 통째로 사라지며 초점이 `<body>` 로 떨어지고 결과가 라이브 영역이 아니던 것, 서식 편집기의
`contenteditable` 에 초점 표시가 없던 것(axe 는 초점 스타일을 검사하지 못한다), 오류를 `aria-invalid` 로만 알리고 무엇이
잘못됐는지는 아무 데도 안 적던 상품 폼, 이름이 "←" 뿐인 링크, `<span>` 이 `<form>` 을 감싼 헤더.

**제목 단계는 훑기가 직접 센다.** axe 의 `heading-order` 는 best-practice 태그라 이 저장소의 태그 목록(wcag\*)에 걸리지
않아 **한 번도 돈 적이 없었다** — 카테고리·브랜드·검색이 h1 다음에 곧바로 상품 카드의 h3 를 놓고 있었고, 운영 기획전은
제목이 h1 하나뿐이었다. best-practice 를 통째로 켜면 취향이 섞인 규칙이 함께 오므로, 필요한 이 하나만 직접 센다(axe 를
한 번 더 돌리지 않아 훑기가 느려지지도 않는다).

**수수료율은 슈퍼관리자가 정하고, 바꿔도 지난 정산은 그대로다.** 스키마에는 가맹점마다 요율 칸이 있었는데 **바꿀 길이
시드밖에 없었다** — 조건을 새로 협의해도 코드를 고쳐 다시 시드해야 했고, 그건 운영이 아니라 배포다. 입점을 승인하는
사람이 조건도 정한다(`merchant:approve`): 관리자가 요율을 내리고 지급까지 집행할 수 있으면 확정과 지급을 갈라 둔 뜻이
없어진다. 0~50% 만 받는다 — 0 은 입점 초기 무수수료 조건이 실제로 있어서 두고, 위를 끊은 것은 0 하나를 더 눌러 5%가
50%가 되는 실수를 거르기 위해서다. **사유를 함께 받아 감사 로그에 남긴다**: 숫자만 바뀐 기록은 "왜 12% 가 됐는가" 에
답하지 못한다.

그러면서 조용한 결함 하나를 찾았다. **정산 행이 금액만 얼리고 요율은 안 들고 있었다** — 내역 CSV 는 가맹점의 *지금*
요율로 다시 계산하고 있어서, 요율을 바꾸면 지난달 파일의 수수료가 확정된 행과 어긋난다. 둘 다 우리가 준 숫자인데 서로
다르면 가맹점은 어느 쪽도 믿을 수 없다. 이제 확정이 금액과 **요율을 함께** 얼리고, 지난 기간의 파일과 표는 그때의
요율로 적는다. 이미 쌓인 행은 얼려 둔 금액에서 되짚어 채웠다(지금 요율을 적어 넣으면 그 행이 실제로 무엇으로 만들어졌는지와
어긋날 수 있다).

**정산 계좌 없이 "지급됨" 을 만들지 않는다.** 스키마에는 계좌 칸이 처음부터 있었는데 **읽는 곳도 쓰는 곳도 없었다** —
한 번도 적지 않은 가맹점의 정산도 눌러 지급이 됐다. 돈이 어디로 갔다는 말인지 아무도 답할 수 없는 기록이다. 이제 계좌가
없으면 지급을 막고(반품지가 없으면 반품을 승인할 수 없게 한 것과 같은 자리), 정산 표에 보낼 곳을 뒤 네 자리만 적는다 —
되돌릴 수 없는 단추를 누르는 화면이 돈이 어디로 가는지 말하지 않고 있었다. **가맹점이 자기 연락처와 계좌를 적고, 사업자
정보(상호·사업자등록번호·대표자)는 운영진만 고친다**: 정산과 세금계산서가 그 값을 근거로 삼으므로 스스로 바꿀 수 있으면
받는 주체가 심사 없이 바뀐다 — 창구도 둘로 나눴다(한 창구로 받아 놓고 안에서 칸을 거르면, 화면이 안 보여 주는 칸을 요청에
끼워 넣는 길이 남는다). 은행은 고르게 한다(자유 입력이면 "국민"·"국민은행"·"KB국민" 이 한 표에 섞인다), 계좌번호는 숫자만
남겨 저장하고(하이픈 유무로 같은 계좌가 둘이 되면 바뀌었는지 알 수 없다), **감사 로그에는 뒤 네 자리만 남긴다.**

**쓴 리뷰를 고친다 — 고쳤다는 사실과 함께.** 창구(PATCH)는 처음부터 있었는데 화면이 없어서, 오타 하나를 고치려면 지우고
다시 쓰는 수밖에 없었다. 그러면 도움돼요 표도 판매자 답글도 함께 사라진다. 이제 마이페이지가 **쓸 것과 쓴 것**을 한 자리에
모으고, 고치는 화면은 쓴 그대로를 채워 두고 연다 — 빈 폼을 주면 한 글자를 고치려던 사람이 글 전체를 잃는다. 사진은 남길
것을 보낸다(뺄 것을 받으면 다른 탭에서 먼저 한 장을 뺐을 때 엉뚱한 사진이 지워진다). 고친 글에는 **수정됨**이 붙는다 —
판매자 답글이 달린 뒤에 원문이 바뀌면 답글이 엉뚱해 보이는데, 표시가 없으면 읽는 사람은 그 이유를 알 길이 없다. 다만
아무것도 안 바꾸고 저장만 누른 사람에게는 붙이지 않는다: 그 표시는 실제로 달라졌을 때만 뜻이 있다. `updatedAt` 으로는
답할 수 없어 `editedAt` 을 따로 둔다 — 도움돼요 표가 오갈 때도 그 행은 갱신된다. 사진을 올리는 자리가 되면서 수정·삭제
창구에도 요청 제한을 걸었다(면제 사유가 더는 참이 아니다).

**메일 문구도 운영이 고친다 — 말만.** 주문 완료·입금 대기·입금 확인·재입고·문의 답변 메일의 제목·머리말·첫 문장을
종류·언어마다 고칠 수 있고, 비운 칸은 사전의 기본 문구로 나간다. 상품 표·금액·계좌·버튼·바닥글은 코드가 그린다 —
거기까지 열면 말투가 아니라 거래 내용을 바꿀 수 있게 된다. 인증·비밀번호 재설정 메일은 넣지 않았다: 운영 실수로
"본인이 요청하지 않았다면 무시하세요" 가 사라지면 피싱과 구분할 단서가 없어진다. 칸마다 끼울 수 있는 값은 코드가
정하고(알림 문구와 같은 검사), **미리보기는 실제로 보내는 함수가 예시 주문으로 만든 메일**을 격리한 틀에 보여 준다 —
화면에서 흉내 내 그리면 실제 메일과 어긋나도 모른다. 메일을 만드는 코드가 칸마다 그 값을 넘기는지는 검사가 모든 메일을
실제로 만들어 확인한다.

**숫자는 지난 기간과 나란히 본다.** "이번 주 순매출 320만원" 은 지난주가 얼마였는지 모르면 뜻이 없다. 대시보드는 탭(오늘·7·30·90일)
외에 날짜를 직접 고를 수 있고(KST 달력, 90일까지 — 원본 이벤트 보존 기간과 같아 더 길면 지워진 날의 트래픽이 0 으로 잡힌다),
지표마다 같은 길이의 바로 앞 기간 대비 증감을 적는다. **오늘이 들어간 기간은 지금 시각까지만 비교한다** — 오전 10시의
"오늘" 을 어제 온종일과 견주면 매일 아침 대시보드가 "80% 줄었다" 고 말한다. 이번·지난 기간은 한 함수(`loadKpi`)로 세어
비교가 규칙 차이를 재지 않게 했다. 방향은 글(증가·감소)로 적고, 늘어난 것이 늘 좋은 것은 아니라 색으로 좋고 나쁨을 칠하지
않는다. 전환율의 차이는 %p 로, 지난 기간이 0 이면 퍼센트 없이 차이만 적는다.

**상품 복제는 틀만 가져온다.** 옵션 묶음·값·추가금·판매 여부·가격·설명·사진은 가져오고, 재고(0)·게시 상태(임시저장)·
리뷰·별점·판매량·찜·기획전은 두고 온다 — 사본이 원본의 평판을 들고 매대에 오르면 안 된다. 이름엔 "(사본)", 주소는
`-copy`, SKU 는 `-C` 를 붙여 원본과 한눈에 갈리게 하고, 겹치면 다음 후보로 간다(보관해도 주소·SKU 는 그대로 쥐고 있어 사본이 쌓이므로
스무 벌을 넘으면 시각으로 번호를 짓는다). 사진은 파일을 새로 올리지 않고 같은 파일을 가리키는데, 그러면 원본에서 사진을
지울 때 사본 사진까지 깨진다 — 그래서 사진을 지울 때 **같은 파일을 쓰는 다른 상품이 있으면 파일은 남긴다.**

**상품은 지우지 않고 보관한다.** 주문 줄이 옵션을 가리키고 있어 행을 지울 수 없고, 지울 수 있더라도 지난 주문·정산·리뷰가
가리킬 것을 잃는다. 보관은 `deletedAt` 을 찍는 일이라 매대·검색·기획전·장바구니가 이미 보던 조건에서 그대로 빠지고, 상태는
건드리지 않아 보관함에서 되돌리면 보관 전 상태로 돌아온다. 누르기 전에 무엇이 멈추고 남는지와 **아직 보내지 않은 주문
건수**를 말한다 — 보관은 새로 파는 것을 멈출 뿐 받은 주문은 보내야 한다. 보관한 쪽(가맹점·운영진)을 적어, 운영진이 내린
상품은 가맹점이 되살리지 못한다. 만들다 보니 **재입고 알림 발송이 상품이 살아 있는지 보지 않고 있었다** — 보관한 상품의
재고를 고치면 눌러도 없는 상품으로 알림이 갔다. 이제 보관한 상품의 대기자는 부르지 않고 남겨 둔다.

**적립금은 손으로도 준다 — 사유와 열쇠를 함께.** 배송 지연 보상이나 잘못 준 적립을 바로잡을 길이 없어 DB 를 직접 고쳐야
했다. 회원 표의 잔액을 누르면 그 사람의 최근 원장 곁에 지급·차감 폼이 있다. 포인트는 돈이라 `user:write` 에 얹지 않고
`point:adjust` 를 따로 두었고(가맹점에게는 없다), 한 번에 10만P 까지, 사유는 필수이며 **손님 적립금 내역에 그대로
보인다**는 것을 칸 곁에 적는다. 보내기 전에 누구에게 얼마, 잔액이 어떻게 바뀌는지 한 번 더 보여 준다. 잔액과 원장은 한
트랜잭션에서 함께 바뀌고(대사 배치가 어긋났다고 잡지 않게), 차감은 "지금 잔액이 차감액 이상" 을 걸고 깎는다 — 반품 회수와
달리 모자라면 있는 만큼 빼지 않고 막는다. 사람이 정한 금액을 조용히 줄여 처리하면 적은 것과 다른 일이 일어난다. 폼마다
열쇠를 만들어 원장의 유일 칸에 넣어, 두 번 누르거나 응답을 못 받고 다시 보내도 **한 번만 나가고 감사 줄도 하나다.**
지급한 포인트는 구매 적립과 같은 유효기간을 갖는다.

**회원 한 사람을 한 화면에 모은다.** 문의를 받은 운영자는 주문·포인트·감사 로그 화면을 오가며 한 사람을 맞춰 봤다. 회원
표에서 이름을 누르면 기본 정보(인증 여부·로그인 방식), 최근 주문 10건과 구매확정 누적액·등급, 포인트 잔액, 리뷰·문의(답변
대기)·쿠폰·찜 수, **운영진이 이 회원에게 한 일**(정지·권한·포인트 조정)이 한 화면에 선다. 긴 목록은 각자의 화면이 갖고
여기는 요약과 거기로 가는 길을 둔다. 정지·탈퇴는 맨 위에 사유와 함께 둔다 — 모르고 주문을 들여다보면 "왜 결제가 안
되냐" 에 엉뚱한 답을 한다. 등급과 누적액은 주문 견적과 같은 함수에서 내서, 운영자가 본 등급과 손님이 받는 적립률이
갈리지 않는다.

**주문 곁에 내부 메모를 남긴다 — 누가 읽는지 갈라서.** 손님 전화("부재 시 경비실", "선물이라 가격표 빼 주세요")나 출고 사정을
적어 둘 곳이 없어 운영진끼리 따로 전했다. 주문 상세에 메모를 남기면 쓴 사람·쪽·시각과 함께 쌓인다. 손님에게는 어디에도
보이지 않고, **운영진 메모는 가맹점이 못 본다** — 상담 내용에는 손님의 사정이 담기는데, 그 주문에 상품 하나 넣은 가맹점이
읽을 말이 아니다. 가맹점 메모는 그 가맹점과 운영진이 본다. 보는 범위는 읽고 거르지 않고 조회 조건으로 건다. 고치기는
없고 쓴 사람만 지운다(지운 내용은 감사 로그에 남는다) — 남긴 말이 나중에 바뀌면 그때 무엇을 알고 있었는지 되짚을 수 없다.

**리뷰에는 파는 사람이 답한다 — 내리지는 못한다.** 가맹점은 자기 상품의 혹평을 내릴 수 없지만(`review:moderate` 는
운영진만) 해명할 자리는 있어야 해서 `review:reply` 를 따로 두었다. 답은 원문을 건드리지 않고 리뷰 **안에** 판매자 답글로
붙는다(어느 글에 한 답인지 떨어져 있으면 모른다). 남의 가맹점 리뷰는 없는 리뷰로 답해 id 를 넣어 보는 것으로 무엇이 누구
것인지 새지 않고, 내려진 리뷰에는 달지 않는다. 처음 답할 때만 쓴 사람에게 알림이 가고(오타를 고칠 때마다 알림함이 차지
않게), 고치면 화면에 "수정됨" 이 붙는다 — 조용히 바뀐 답은 읽은 사람이 무엇을 봤는지 모르게 한다. 공개로 한 말이라 전후를
감사 로그에 남기고, 상품 화면의 리뷰 캐시를 턴다.

**파는 사람은 이 매대의 평을 쓰지 않는다.** `review:write` 는 처음부터 고객과 운영진에게만 줬는데 **어디서도 검사하지
않아서**, 34개 권한 중 유일하게 강제 지점이 0이었다 — 선언만 하고 연결하지 않으면 없는 규칙이다. 가맹점이 자기 상품을
사서 자기가 별 다섯을 쓰면 그 별점이 상품 정렬 점수(`ratingScore`)로 곧장 들어가 매대의 차례를 바꾸고, 리뷰 적립금까지
자기가 받는다. 자기 상품만 가리지 않는다 — 파는 사람의 계정으로 쓴 평은 칭찬이든 혹평이든 그것이 무엇인지 확신할 수
없다. 막는 김에 쓸 것 목록과 마이페이지 뱃지도 같은 조건을 보고, 빈 화면에는 "쓸 것이 없다" 대신 까닭을 적는다. 이미 써
둔 평을 고치는 것은 막지 않는다. 같은 구멍이 다시 나지 않게 **선언한 권한에 강제 지점이 있는지**를 검사가 훑는다
(`permission-coverage`).

**회원정보는 서버에서 두 번 본다.** 이름·연락처는 우리 창구가 계약으로 먼저 막고(칸마다 우리 말 문구), 저장은 인증
라이브러리의 사용자 수정을 서버에서 불러 한다 — DB 를 직접 고치면 세션 쿠키 캐시(5분)에 옛 이름이 남아 머리에 한동안
옛 이름이 뜬다. 라이브러리의 사용자 수정 창구는 누구나 직접 부를 수 있어서, 사용자 수정 훅이 같은 규칙으로 한 번 더
막는다. 비밀번호 변경은 지금 비밀번호를 묻고(빌린 기기로 계정을 가져가지 못하게) 다른 기기의 로그인을 끊는다. 틀린 지금
비밀번호는 그 칸에 알리고, 구글로 가입한 계정에는 비밀번호 칸 대신 그 사실을 적는다. 이메일은 새 주소 확인 없이 바꿀 수
없어 여기서 고치지 않는다.

**교환을 신청하면 환불이 됐다.** 손님은 교환을 고를 수 있었지만 처리하는 쪽은 신청 종류를 보지 않아, 운영 화면의
"회수 확인 · 환불" 을 누르면 돈이 나가고 바꿀 물건은 가지 않았다. 이제 교환은 **돈이 움직이지 않는 반품**으로 끝이
다르다. 손님이 줄마다 바꿀 옵션을 고르고(같은 상품·같은 추가금 — 차액이 생기면 그것은 반품과 새 주문이다), 신청하는
순간 그 옵션의 재고를 조건부로 잡는다(승인을 기다리는 사이 팔려 나가면 보낼 물건이 없다). 반려하면 풀어 주고,
처리하는 쪽은 환불 단추 대신 교환 상품 송장을 적는다 — 돌아온 옵션 재고가 늘고, 주문 줄은 손님이 지금 가진 옵션을
가리키며(처음 산 옵션은 교환 줄에 남는다), 주문은 신청 전 자리로 돌아간다. 돈이 안 움직여 가맹점도 자기 상품 교환을
끝까지 처리한다. 반품 환불 창구는 교환 신청을 거절한다. 보내면 손님에게 **알림함과 메일로** 알린다 — 신청한 뒤
승인·회수·발송을 기다리는 사람은 알리지 않으면 주문 화면을 다시 열어야 교환이 끝났는지 안다. 메일에는 무엇이 무엇으로
바뀌어 가는지(상품: 이전 옵션 → 새 옵션)와 송장을 적고 조회 단추를 단다. 문구는 다른 메일·알림처럼 운영이 고칠 수 있다.

**취소·반품 결과·환불도 손님에게 알린다.** 전에는 출고·배송완료만 알려, 돈이 돌아가는 일과 반품 신청의 결과는 주문 화면을
다시 열어야 알았다. 이제 주문 취소(전체·일부, 결제 대기 만료 포함), 반품·교환 승인·반려, 환불 완료를 **메일로** 보내고,
**알림함에는 남이 한 일만** 남긴다 — 손님이 스스로 취소한 것까지 알림함에 뜨면 소음이다. 돈이 걸린 메일은 환불 금액·
돌려준 포인트·뗀 배송비를 따로 적고 카드 환불이 늦게 보이는 이유를 붙인다. 승인 메일에는 다음에 할 일을, 반려 메일에는
사유를 적는다. **운영진의 취소 메모는 손님에게 보이지 않는다**(손님에게 쓴 말이 아니다). 취소·환불 함수는 서로를
부르므로(일부 취소가 전부가 되면 주문 취소로, 반품 회수가 환불로) 알림은 처리를 시작한 창구에서 한 번만 보낸다.

**운영진이 계정에 한 일도 알린다.** 적립금을 손으로 주거나 빼면 메일과 알림함으로 사유·지금 잔액·(지급이면) 소멸 예정일을
알린다 — 같은 열쇠로 다시 온 요청에는 알리지 않는다. 이용 정지는 **메일로만** 사유와 함께, 무엇이 막히고(로그인·새 주문)
무엇은 그대로인지(결제한 주문의 배송·환불) 적어 알린다. 정지된 사람은 알림함을 열 수 없고, 풀린 뒤에 열면 지난 "정지되었습니다"
가 맨 위에 있어 아직 막힌 줄 안다. 풀리면 메일과 알림함 둘 다로 알린다.

**배송지는 지우지 않고 고친다.** 오타 하나를 고치려면 지우고 다시 넣어야 했는데, 그러면 기본 배송지가 지워지며 다른 주소가
기본으로 올라가고 새로 넣은 것이 맨 위로 가 — 한 칸 말고 두 가지가 더 바뀌었다. 이제 줄마다 수정이 있고, 그 줄이 지금 값으로
채운 폼이 된다. 우편번호를 고치면 도서산간을 다시 판정하고, 기본 여부는 고치는 창구에서 바꾸지 않는다(내리면 기본이 없는
상태가 된다). 이미 한 주문은 배송지를 복사해 들고 있어 바뀌지 않는다는 것을 폼에 적는다. 저장·취소 뒤에는 초점이 그 줄의
수정 단추로 돌아온다.

**반품·교환은 대기열에서 누구 차례인지 본다.** 반품은 둘이 나눠 처리한다 — 승인·반려와 물건 도착 확인은 물건 곁의 가맹점이
(남의 상품이 섞였으면 운영진이), 돈을 내보내는 환불은 운영진이. 주문 목록을 "반품접수" 로 거르면 신청이 어디까지 왔는지가 안
보여 가맹점은 운영진이 환불할 줄, 운영진은 가맹점이 확인할 줄 알고 서로 기다렸다. 이제 신청을 **단계**(승인 대기 → 물건 도착
대기 → 환불·교환 발송 대기 → 끝남)로 나눠 탭마다 수를 붙이고, 줄마다 **내 차례**를 글자로 붙인다. 진행 중인 것은 오래 기다린
것부터, 사흘이 넘으면 눈에 띄게 적는다. 단계 조회 조건과 단계 판정이 같은 갈래인지는 검사가 모든 조합을 돌려 맞춘다. 처리는
여전히 주문 상세 한 곳에서 한다(돈과 재고를 움직이는 곳을 둘로 만들지 않는다).

**약관과 개인정보처리방침은 지난 판까지 남긴다.** 결제 화면이 "개인정보 수집·이용 및 결제대행 약관에 동의합니다" 를
필수로 받고 있었는데 **읽을 문서가 없었다** — 무엇에 대한 동의인지 아무도 말할 수 없는 동의였다. 이제 두 문서를 공지·FAQ 와
따로 두고(한 벌이고, 시행일이 있고, 지난 이력이 남는다) 푸터·가입·결제에서 그 주소를 가리킨다. 저장은 덮어쓰기가 아니라
갈아 끼우기다 — 바뀌기 전 내용이 지난 방침으로 남고 손님 화면에서 그 주소로 다시 열린다. 동의 기록은 **시각 하나**만
남기는데(User.termsAgreedAt), 그날 무엇에 동의했는지는 지난 이력이 답하기 때문이다. 시행일은 올린 날과 따로 받는다 —
개인정보처리방침은 바꾸기 전에 미리 알려야 해서 "며칠 뒤부터" 로 먼저 올리고, 그동안 효력을 갖는 것은 지난 방침이다.
가입 동의는 필수(약관·개인정보 수집)와 선택(마케팅 수신)을 눈으로 가르고, 선택은 마이페이지에서 언제든 철회한다 —
**철회할 길이 없으면 동의가 아니다.**

**반품지는 판매처가 쥐고, 손님에게는 승인한 뒤에 보여 준다.** 반품을 승인해 놓고 보낼 곳을 알려 주지 않으면 손님은
받은 상자에 적힌 출고지로 보내거나 고객센터에 묻는다 — 출고지가 물류 대행사면 물건이 엉뚱한 곳에 도착해 아무도 도착을
확인하지 못한다. 그래서 가맹점마다 반품지를 하나 두고 가맹점이 직접 고치며(자사 브랜드 상품은 가게 전체의 약속이라
배송비 화면에 플랫폼 반품지를 둔다), **반품지가 없으면 승인 자체를 막는다** — 승인 알림에 적을 주소가 없는 채로
대기열에 남는 신청을 만들지 않는다. 손님 주문 화면과 승인 메일에는 승인했고 아직 물건이 도착하지 않은 동안에만 적고,
한 신청에 두 판매처 상품이 섞였으면 주소를 둘 다 적고 **상자를 나눠** 보내라고 말한다(한 주소만 적으면 한쪽 물건이 남의
창고로 간다).

**곧 사라질 쿠폰·적립금은 한 주 전에 한 번 알린다.** 적립금 화면에 소멸 예정일을 날짜별로 보여 주지만 들어와야 보이고,
쿠폰은 쓰려고 할 때에야 기한이 지난 것을 안다. 매일 KST 10:00 배치가 7일 안에 사라질 것을 사람마다 한 통(쿠폰 한 통, 적립금
한 통)으로 모아 메일과 알림함으로 알린다 — 쿠폰마다 이름과 기한, 적립금은 날마다 얼마가. 적립금은 이미 쓴 몫을 빼고 센다(먼저
사라질 것부터 썼다고 보는 소멸 규칙 그대로). **알린 쿠폰·적립 줄에 알린 때를 적어** 한 번만 알리고, 날짜 창(정확히 7일 뒤
하루)으로 거르지 않는다 — 배치가 하루 빠지면 그날 기한인 것이 영영 안 알려진다. 표시를 먼저 하고 보내, 실패하면 알림 하나를
놓칠 뿐 같은 알림을 매일 받지는 않는다. 운영이 내린 쿠폰·이미 쓴 쿠폰·탈퇴한 계정은 알리지 않는다.

**쿠폰은 코드 없이도 받는다.** 쿠폰은 코드 입력과 운영 지급으로만 받아, 코드를 모르면 있는 쿠폰도 없는 것이었다. 운영이 쿠폰을
**누구나 받기**로 공개하면 쿠폰 받기 화면(`/coupons`, 로그인 없이도 본다)과 **그 쿠폰이 쓰이는 상품 화면**에 받기 단추로 뜬다 —
상품 화면에 그 상품에 못 쓰는 쿠폰을 내밀면 받고 나서 헛걸음한다(대상 판정은 장바구니 할인과 같은 뜻). 받으면 단추가 사라지지
않고 같은 자리가 "받음" 이 되어 초점이 튀지 않는다. 받는 창구는 **공개한 쿠폰만** 준다 — 쿠폰 id 는 화면에 드러나 있어, 공개
여부를 안 보면 보상용·코드용 쿠폰을 id 만으로 받아 갈 수 있다. 수량·중복·기간은 코드 입력과 같은 발급 함수가 조건부로 막는다.

**1:1 문의에는 사진을 붙인다.** 불량·오배송은 글보다 사진이 빠르다. 한 문의에 3장까지, 리뷰 사진과 **같은 길**(파일 내용으로
형식 검사 · 찍은 위치 정보 제거 · 파일 이름 대신 추측할 수 없는 키 · 중간에 실패하면 올린 것 되돌리기)을 지나고, 그 길은
리뷰와 문의가 함께 쓰도록 한 곳으로 모았다. **상품 문의에는 받지 않는다** — 상품 문의는 공개 Q&A 라, 손님의 물건·집 사진이
상품 화면에 걸린다. 창구는 그런 요청을 올리기 전에 거절해 저장소에 파일이 남지 않게 한다. 사진은 쓴 사람의 문의 목록과
답하는 운영진·가맹점 목록에만 보인다. 저장소를 설정하지 않은 배포에서는 사진 칸을 내밀지 않는다 — 고르고 보냈는데 실패하면
쓴 글까지 다시 써야 한다. 주소는 공개 저장소에 있으므로 비공개 문의의 사진도 주소를 아는 사람은 열 수 있다(키를 추측할 수
없게 두는 것으로 막는다).

**구매확정은 기다려야만 됐다.** 배송완료 뒤 며칠이 지나야 배치가 확정해, 받자마자 괜찮다고 느낀 손님도 적립금을
기다렸다. 이제 주문 화면에서 스스로 확정한다. 누르면 먼저 무엇이 바뀌는지 — 적립금이 바로 들어오고 단순 변심 반품이
닫힌다(불량·오배송은 남는다) — 를 확정 단추에 묶어 말하고, 한 번 더 눌러야 확정된다. 반품·교환이 진행 중이면 단추가
없다. 확정과 적립은 배치와 **같은 함수**를 지나고(배송완료일 때만 조건부로 바꿔 둘이 겹쳐도 한 번만 적립), 성공하면 단추가
사라지므로 결과는 주소에 실어 화면이 말한다. e2e 는 자기 손님으로 사서 받고 확정해, 적립금 잔액이 정확히 그만큼 늘고
반품 사유에서 단순 변심이 빠지는지 본다.

**재입고 알림 신청이 어디서도 열리지 않고 있었다.** 신청 단추는 품절 옵션을 골라야 뜨는데, 품절 옵션이 눌리지 않게
막혀 있었다(aria-disabled, 클릭 무시). 옛 검사는 품절 상품에 들어가 "품절" 글자만 보고 끝나 몰랐다. 찜·재입고 화면 e2e 를
사람이 밟는 길 그대로 쓰면서 드러났고, 품절 옵션을 고를 수 있게 바꿨다 — 이름에 "품절" 이 함께 읽히고, 고르면 담기·수량
대신 재입고 알림이 뜬다. e2e 는 자기 손님·자기 상품으로 옵션 하나를 품절로 내리고, 신청 → 마이페이지 목록 → 운영 화면에서
재고 채우기 → 알림함의 재입고 알림 → "재입고됨" → 삭제까지 잇고, 찜은 상품 화면과 찜 목록 사이를 오간다.

**알림 문구는 운영이 고치고, 끼울 값은 코드가 정한다.** 종류·언어마다 템플릿을 두고 줄이 없으면 사전의 기본 문구를
쓴다 — 기본 문구를 복사해 저장하지 않으므로 사전을 고치면 손대지 않은 종류는 따라 바뀐다. `{이름}` 자리는 그 알림에
실제로 실리는 값만 쓸 수 있고(`NOTIFICATION_PARAMS`, 알림을 남기는 코드와 같은지 검사가 소스를 읽어 맞춘다), 없는 값·짝이
안 맞는 중괄호는 적는 순간 화면이 알리고 서버도 같은 검사로 막는다. 알림에는 문장이 아니라 값만 저장하므로 **이미 온
알림도 새 문구로 읽힌다** — 그래서 전후 문구를 감사 로그에 남긴다. 값이 빠진 옛 알림은 고친 문구 대신 기본 문구로
물러난다(`{productName}` 이 글자로 보이지 않게).

**감사 로그는 좁혀 보고, 그 조건 그대로 내려받는다.** 기간(KST, 끝날 포함 — 주문 검색과 같은 함수)·행위자(배치는
"자동 실행" 한 칸)를 더했고, 목록과 파일이 **한 조건 함수**(`auditLogWhere`)를 쓴다. 파일에는 이름표와 원래 코드를 둘 다
싣고(이름표는 바뀌어도 코드는 맞춰 볼 기준이다), 한도를 넘으면 앞 일부를 잘라 주지 않고 거절한다 — 일부만 담긴 파일은
"그 기간 전부" 로 읽힌다. **내려받은 사람도 기록에 남는다.** 이름표를 모으다 동작 열여덟 개가 이름 없이 코드로 나가고
있던 것과, 운영진의 문의 삭제가 대상 "리뷰" 로 적히던 것을 찾아 고쳤다 — 이제 기록하는 동작마다 이름표가 있는지 검사가
소스를 읽어 확인한다.

**포인트 소멸은 날짜별로 보여 준다.** "30일 안에 ○○P" 한 줄로는 다음 주인지 29일 뒤인지 몰라 지금 쓸지 정할 수 없다.
어떤 사용이 어떤 적립을 썼는지는 원장에 없어서 기한이 가까운 것부터 쓴 것으로 짝짓는데, **소멸 배치와 화면이 같은
짝짓기 함수**를 쓴다 — 따로 계산하면 화면이 예고한 금액과 실제로 사라지는 금액이 갈린다. 날짜는 KST 달력으로 자르고
(UTC 로 자르면 자정 넘어 기한인 포인트가 하루 앞 날짜에 묶인다), 30일 안의 합이 위의 한 줄 요약과 같은지 검사가 본다.

**영수증은 화면과 종이가 같은 마크업이다.** PDF 를 따로 만들면 화면에서 본 숫자와 종이의 숫자가 갈릴 수 있어서,
브라우저 인쇄로 뽑고 인쇄할 때만 가게 머리·발과 단추를 뺀다(`print:hidden`). 어두운 테마를 고른 사람도 흰 종이에
흰 글자가 찍히지 않게 인쇄에서는 밝은 값으로 되돌린다. 흑백으로 찍혀도 뜻이 남도록 취소된 줄은 흐리게가 아니라
글자로, 할인은 빼기 부호로 적는다. 결제 금액은 줄여 적지 않고 돌려준 돈과 **실제 낸 돈**을 따로 적는다 — 주문
상세와 같은 함수(`receiptTotals`)로 더한다. 결제 전 주문에는 영수증을 내지 않는다(내지 않은 돈의 증빙이 된다).
사업자 정보가 없는 포트폴리오라 세금계산서·현금영수증이 아니라고 밝혀 둔다.

**정지는 상태가 아니라 끊기다.** 표시만 바꾸면 이미 로그인해 둔 사람은 세션이 끝나는 30일 동안 그대로 쓴다.
그래서 정지하는 트랜잭션에서 그 회원의 세션을 전부 지우고, 새로 로그인하는 순간은 **세션을 만드는 자리**(better-auth
세션 생성 훅)에서 막는다 — 비밀번호·구글·가입 직후 자동 로그인이 모두 거기를 지나서 창구마다 검사를 붙일 필요가
없고, 비밀번호 확인 뒤라 틀린 비밀번호로는 정지 여부를 캐낼 수 없다. 로그인 화면은 "틀렸다" 가 아니라 "정지됐다"
고 말한다. 남는 틈은 세션 쿠키 캐시(5분)라, 재고를 묶는 **주문 창구만 DB 를 다시 본다**. 관리자는 운영진을 정지할
수 없고(슈퍼관리자만), 사유는 필수이며 감사 로그에 남는다. 비밀번호와 연결 계정은 지우지 않아 풀면 그대로 돌아온다.

**내려받은 파일이 곧 송장 양식이다.** 주문 CSV 는 목록과 같은 조건 함수로 뽑고, 상품
한 줄씩 펼치며, 손님 계정의 값(주문자 이름·이메일·등급)은 **고르지도 않는다** — 받는
사람의 이름·연락처·주소만 배송에 필요해서 준다. 칸이 `=`·`+`·`-`·`@` 로 시작하면
작은따옴표를 붙여 엑셀이 수식으로 실행하지 않게 하고, 누가 어떤 조건으로 몇 줄을
가져갔는지 감사 로그에 남긴다. 그 파일의 택배사·송장번호를 채워 올리면 **한 건 등록과
같은 함수**를 줄마다 부른다(범위·상태 검사·감사 로그가 갈리지 않게). 한 줄이 틀려도
나머지는 들어가고 틀린 줄은 줄 번호와 사유로 돌아온다. 한국어 엑셀이 저장한 CP949
파일도 읽는다. 처음에는 **파일을 통째로 다시 올리면 값이 그대로인 주문까지 "등록"
으로 세고** 감사 로그를 줄마다 쌓았다 — e2e 가 잡았고, 이미 같은 송장은 건드리지
않고 따로 센다.

**칸은 있는데 아무도 안 채우고 있었다.** 이벤트 표에 `merchantId` 가 있는데 개발 DB
1만 7천 건 중 **0건**이었다 — 그래서 가맹점은 자기 상품이 몇 번 조회되고 몇 번
담기는지 볼 수 없었고, 대시보드도 퍼널을 주지 않았다. 값은 **상품에서 끌어온다**:
본문에 적어 보내게 하면 아무나 남의 가맹점 지표를 부풀릴 수 있다(userId 를 세션에서만
읽는 것과 같은 이유). 가맹점 퍼널은 **세 단계**다 — 주문서 진입은 장바구니 전체의
일이라 한 가맹점에 귀속되지 않는다. 결제는 이벤트가 아니라 **주문**에서 센다:
purchase 이벤트는 주문 하나에 하나뿐이라 여러 가맹점이 섞인 주문에 달 수 없다.

**앱이 느린지 아닌지를 말할 수 없었다.** 실사용자 성능(web-vitals)은 진작 모으고
있었는데, 이벤트에 붙는 구분은 UA 에서 뽑은 기기 종류(mobile·tablet·desktop)뿐이라
**앱 웹뷰가 모바일 브라우저와 같은 칸**에 들어갔다. 둘은 같지 않다 — 앱은 켤 때마다
웹뷰를 차게 띄우고 브라우저가 쥔 것(따뜻한 연결, 지난 방문의 캐시)을 하나도 물려받지
못한다. 그 값이 섞이면 둘 다 뿌옇게 된다. 실기기에서 재 보니 냉시작 첫 그림까지
1.3초, 마지막 요청까지 7.7초였는데 이 숫자가 어느 쪽 몫인지 가릴 방법이 없었다.

그래서 봉투에 `platform`(web·ios·android)을 싣는다. **이것만은 브라우저가 말한 것을
받는다** — userId·receivedAt·ipHash 는 서버가 덮어쓰지만 이건 서버가 알 방법이 없다:
iOS 웹뷰의 UA 는 사파리와 구분되지 않는다. 돈이 걸린 값도 아니라(클라이언트를 안 믿는
원칙은 purchase·refund 에 걸리는 말이다) 지어내 봐야 자기 쪽 통계만 흐려진다. 안
보내도 받는다 — 배포 직후에는 옛 스크립트를 쥔 화면이 남아 있고, 그것 때문에 이벤트를
통째로 버리면 잃는 쪽이 더 크다. 모르는 값은 `web` 으로 접지 않고 비워 둔다. 지난
행과 서버가 직접 적은 이벤트도 빈 채로 두고, 전체에만 세고 플랫폼 칸에는 안 넣는다 —
어디서 왔는지 모르는 것을 어느 칸에 넣어도 거짓이 된다. 운영 화면은 전체·웹·iOS·
안드로이드를 한 표에 나란히 놓는다(전체와 플랫폼 줄을 `grouping sets` 로 한 질의에서
받는다 — 따로 물으면 같은 표를 네 번 훑는다).

**주문이 쌓이면 목록은 쓸모가 없어진다.** 내 주문 화면은 상태 탭 하나만 받고 스무
건만 보여 주는데 넘길 길도 없어서, 스물한 번째 주문부터는 주소로도 못 갔다 — "작년에
산 그 코트" 를 찾는 길이 없었다. 검색(주문번호·상품명)과 기간을 더했다. 검색어를
읽는 규칙은 운영자 쪽과 **같은 곳**에 둔다(주문번호 모양이 바뀔 때 한쪽만 고쳐지지
않게). 다만 나머지를 운영자는 **사는 사람 이름**으로, 손님은 **상품명**으로 읽는다 —
손님은 자기 주문만 보므로 이름으로 찾을 일이 없다.

**값은 운영이 정하고 규칙은 코드가 갖는다.** 배송비 3,000원·무료 5만원·도서산간
3,000원이 `packages/core` 의 **코드 상수**여서, 무료 기준을 3만원으로 내리려면 배포를
해야 했다 — 운영에서 가장 자주 바뀌는 값 중 하나가 그랬다. 값을 표로 옮기고 운영
화면에서 고치게 했다. "무료 기준을 넘으면 기본료를 받지 않는다" 는 **규칙**은 그대로
코드에 있다 — 그것까지 데이터로 만들면 아무도 그 동작을 읽을 수 없게 된다.

옮기는 것보다 어려운 것은 **읽는 자리를 하나도 빠뜨리지 않는 것**이었다. 정책을 읽는
자리가 넷이다(견적·상품 화면 안내·비교의 무료배송 표시·배송지의 도서산간 안내).
그중 셋은 `use client` 라 DB 를 못 읽어 서버가 내려보낸다 — prop 을 **필수**로 두었더니
타입 검사가 빠뜨린 두 자리를 정확히 짚어 주었다.

**읽는 것과 내리는 것을 갈랐다.** 한동안 가맹점은 자기 상품의 평을 **보지도**
못했다 — 문의는 답까지 하게 해 두었으면서. 그때 적어 둔 이유("자기 상품의 혹평을
내릴 수 있으면 리뷰가 상품 설명의 일부가 된다")는 지금도 맞지만, 그건 **내리는 것**에
걸리는 말이지 읽는 것에 걸리는 말이 아니었다. 그래서 `review:read` 를 따로 두고
`review:moderate` 는 운영진에게 남겼다. 권한을 낮추는 것만으로는 부족해서 조회에
`merchantScope` 를 함께 걸었고, 그 범위를 걷어 내면 e2e 가 잡는다.

**마지막 한 개를 두 사람이 동시에 산다.** 재고 차감은 조건부 UPDATE 로 짜여 있는데
(읽고 나서 쓰면 두 주문이 같은 재고를 보고 둘 다 성공한다), 주문 만들기의 단위 검사는
Prisma 를 통째로 흉내 내므로 **`updateMany` 가 0 을 돌려주는 상황을 내가 적어 넣는다** —
데이터베이스가 정말 그렇게 동작하는지는 그 검사가 말해 줄 수 없다. 그래서 진짜
Postgres 를 상대로 두 요청을 같은 순간에 던지고, **남은 재고가 음수가 아닌지**를 본다.
읽고-나서-쓰기로 바꿔 보면 −1 이 되어 잡힌다.

**한 장짜리 쿠폰이 두 주문에 붙지 않는다.** 주문 여섯을 한꺼번에 던진다 — 손이
미끄러져 두 번 누르거나 창을 여러 개 띄워 놓으면 실제로 이렇게 된다. 다만 이쪽은
**결과만** 지킨다: 조건부 UPDATE 를 읽고-나서-쓰기로 바꿔 놓고 던져 봤는데 검사가
그대로 통과했다. 요청들이 트랜잭션 창에서 겹치지 않고 줄 서서 처리돼 바깥쪽 조회가
먼저 막은 것이다. 밖에서 그 창을 겹치게 만들 방법을 아직 못 찾았고, 그래서 그
사실을 명세에 적어 두었다.

**가맹점에게 돈이 나가는 길도 화면에서 밟는다.** 정산 화면은 훑기만 당하고 있었다 —
자리·대비 검사가 열어 보기는 했지만 아무도 숫자를 읽지 않았고, 확정도 지급도 눌러
본 적이 없었다. 이제 초안의 줄이 서로 맞는지(매출 − 수수료 − 환불 = 지급액), 확정한
숫자가 그대로 얼어붙는지, 확정과 지급을 **다른 사람이** 하는지, 그리고 같은 정산에
지급이 두 번 나가지 않는지를 e2e 가 본다.

운영 화면은 **폰 폭(375px)까지** 잰다. 예전에는 "운영 콘솔은 폰을 위한 것이
아니다" 라며 768px 부터 쟀는데, 그 폭에서 열여섯 장이 다 걸린 진짜 이유는 표가
아니라 메뉴였다 — 사이드바가 232px 을 늘 차지해 본문에 143px 밖에 안 남았다.

## 배포

Vercel. 프론트와 백이 한 프로젝트라 별도 백엔드 서버가 필요 없고,
API 라우트와 서버 렌더링이 전부 서버리스 함수로 돈다.

- **Root Directory**: 저장소 루트 (`vercel.json` 의 `buildCommand` 가 `--filter=@shop/web` 로 잡는다)
- **Environment Variables**: `.env.example` 의 항목을 대시보드에 등록
- **Region**: `sin1` (싱가포르) — 서울이 아니다. DB 가 싱가포르에 있어서
  함수를 DB 옆으로 옮겼다. 옮기기 전 주문 왕복이 4.2초였고 옮긴 뒤 1.3초다
  (한 요청의 DB 시간 141ms → 7~19ms). 자세한 것은 [docs/DEPLOY.md](docs/DEPLOY.md)

Postgres 와 오브젝트 스토리지는 따로 마련해야 한다. 절차와 환경변수,
"무엇을 비워 두면 무엇이 조용히 꺼지는지" 는 [docs/DEPLOY.md](docs/DEPLOY.md) 에 있다.

주의 — `tooling/docker-compose.yml` 의 Postgres 는 로컬 개발용이다.
프로덕션에서는 서버리스에 맞는 풀링을 지원하는 DB(Vercel Postgres, Neon, Supabase 등)를
써야 한다. 함수마다 커넥션을 새로 여는 구조라 일반 Postgres 는 커넥션이 금방 고갈된다.

## CI

`.github/workflows/ci.yml` — 의존성 권고 → 린트 → 타입체크 → 테스트 → 빌드 →
E2E 를 한 잡에서 돌린다.

**자동 실행은 꺼 두었다.** 이 저장소는 비공개라 Actions 가 분당 과금인데, 한
실행이 Postgres 를 띄워 E2E 까지 전부 돌아 무료 한도를 금방 먹는다. 지금은
`workflow_dispatch` 로 손으로만 돌린다(Actions 탭 → Run workflow). 되돌리려면
그 파일의 `push` · `pull_request` 주석을 풀면 된다.

**그래서 로컬이 문지기다.** 같은 순서로 같은 것을 돌리고 일회용 DB 까지
새로 만든다. 배포는 Vercel 이 Git 연동으로 직접 하므로, 워크플로를 꺼도
**푸시하면 그대로 배포된다** — 저장소 쪽에서 막아 주는 것이 없다.

문지기는 둘이다.

| | 무엇을 | 시간 |
|---|---|---|
| `pnpm ci:quick` | lint · typecheck · build · 단위 | **1분 55초** |
| `pnpm ci:local` | 거기에 e2e 까지 | 5분 30초 |

나눈 이유는 시간이다. 재 보니 전체의 3분의 2가 e2e 였다 — 701개를 진짜
브라우저로 돌기 때문이고, 그중 절반이 화면 × 폭 × 언어의 곱으로 생기는 레이아웃
검사다. **워커를 늘리는 것은 답이 아니었다**: 서버가 하나라 5 → 7 → 10 으로
갈수록 오히려 느려졌고(261초 → 341초), 10 에서는 기다림이 한도를 넘겨 멀쩡한
검사 열다섯이 깨졌다.

**빠른 쪽으로 갈음하지 않는다.** 푸시가 곧 배포라서, 규칙은 **"화면·API·스키마를
건드렸으면 전체"** 다. 문서와 검사만 고쳤을 때가 빠른 쪽의 자리다. 빠른 쪽은
끝날 때 무엇을 안 봤는지 스스로 말한다.

두 문지기가 다른 것을 보지 않도록 **빠른 쪽은 전체의 앞부분이어야 한다** —
뒤를 잘라 낸 것일 뿐이라는 사실을 `ci-order` 검사가 지킨다.

## 알아 둘 것

**TypeScript 는 7.0.2 가 아니라 6.0.3 에 고정돼 있다.** Next 16 의 `typedRoutes` 가
만드는 조건부 템플릿 리터럴 타입을 TS 7 이 잘못 판정해, 멀쩡한 `<Link href="/login">`
에도 에러를 낸다(같은 프로젝트가 TS 6.0.3 에서는 에러 0개). `next build` 의 자체
타입체크는 통과하고 `tsc --noEmit` 만 실패해서, CI 와 빌드가 서로 다른 답을 내는
상태가 된다. typedRoutes 를 끄는 대신 컴파일러를 내렸다. TS 7 이 고쳐지면 되돌린다.

## 실기기에서 확인한 것

갤럭시 S25(SM-S948N, 1080×2340, 밀도 420)에 앱을 설치하고 웹뷰 디버거를 붙여
쟀다. 눈으로 본 것이 아니라 `visualViewport` 와 픽셀 밝기를 읽은 값이다.

- **상태바** — 웹뷰가 `viewport-fit=cover` 로 상태바 아래까지 올라오고 헤더가
  `safe-t` 로 자리를 비운다. 그 위에 뜨는 OS 아이콘의 대비가 **8.6:1** 이다
  (아이콘 기준 3:1). 밝은 헤더 위에서 시계·배터리가 읽힌다.
- **키보드** — 로그인 2칸, 문의 2칸, 배송지 6칸을 하나씩 눌러 봤다. 키보드가
  412px 를 먹어 보이는 높이가 891 → 480 이 되는데, 웹뷰가 초점 받은 칸을 그
  위로 밀어 올린다. **가려지는 칸은 없었다.**
- **결제 화면 8칸** — 받는 사람·연락처·우편번호·주소·상세·별칭·배송 요청·포인트를
  하나씩 눌렀다. 가려지는 칸은 없다.
- **여기서 결함이 하나 나왔다** — 비교함 막대가 장바구니의 `주문하기` 버튼을
  통째로 덮고 있었다. 이제 사는 흐름에서는 비교함을 띄우지 않는다.
